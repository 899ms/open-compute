0.1.9 publishes `@open-compute/sdk`, a version-paired npm client for the qualified Cloudflare-compatible management surface, and adds the weekly Cloudflare upstream-refresh pipeline. The `ocd` binary behavior is unchanged from 0.1.8; this release matters for developers who script account, Worker, KV, D1, R2, Queue, and Workflow management from Node.js or Bun.

## What's new

- **`@open-compute/sdk` published.** The new public npm package is released jointly with this `ocd` tag under the same `X.Y.Z`. `createOpenComputeClient({ apiToken, baseURL })` exposes exactly the 140 management operations `ocd` has qualified against the pinned Cloudflare OpenAPI subset, plus 19 open-compute-only vendor operations under `client.openCompute` (capabilities, system status, scheduler, cache, image capacity, upgrade check, Worker endpoints, Durable Object inventory, and KV/D1 backups). Every standard method delegates to the pinned official `cloudflare@7.1.0` implementation, so authentication, retries, pagination, multipart upload, and `APIError` parsing match the official client. Workers resource limits reach users through the official `workers.scripts.settings.get/edit` types.
- **The client cannot fall back to Cloudflare.** `baseURL` is mandatory, absolute, canonical, and must end in `/client/v4`; plain HTTP is accepted only for loopback test addresses; no ambient credential variables are read; and `defaultHeaders` cannot override `Authorization` or platform-internal headers. The Dashboard now consumes the same closed capability surface.
- **The capability inventory is completed.** `GET /open-compute/capabilities` now advertises `GET /open-compute/upgrade/check` and `GET /accounts/{account_id}/queues/{queue_id}/metrics`: routes `ocd` already served but the authority had never registered. Both are also in the SDK surface.
- **Weekly upstream refresh.** A read-only scanner, three-way classification fixtures, and a scheduled workflow compare the pinned OpenAPI, official SDK, and Wrangler identities and classify each candidate as `ready`, `blocked`, or `breaking` against a single tracking issue. Discovery never moves a formal pin, auto-merges, tags, or publishes.

## Workerd

`third_party/workerd` is unchanged from 0.1.8: revision `d711abf405f2d56b6518a863bb5dbcace14289f1` and formal pin `v1.20260905.0-open-compute-p3.d711abf4`. `workerd --version` still prints `workerd 2026-09-05`; that date string is not the pin identity, so an unchanged version output here means no runtime upgrade, not a failed one.

## SDK

- Package: `@open-compute/sdk@0.1.9`, published to the [npm registry](https://www.npmjs.com/package/@open-compute/sdk); install with `npm install @open-compute/sdk`.
- Pins: official `cloudflare@7.1.0` (npm tarball identity recorded in `release.json`), Cloudflare OpenAPI revision `b8687f42e28fbfcb296a350f7dbf16349ea900af`, API surface digest recorded alongside the package identity in `release.json`.
- Surface change: initial publication; 140 standard operations and 19 `openCompute` vendor operations. The full operation-to-official-method mapping lives in the repository surface report and drives the website API reference.
- Pairing: only an `ocd` of the same `X.Y.Z` release is qualified; a version mismatch fails closed rather than silently aliasing requests.

## Fixed

No `ocd` runtime behavior changed in 0.1.9. The committed OpenAPI authority, capability inventory, and SDK surface now canonicalize through one prettier form across the generator, byte-reproducibility checks, and the pre-commit hook, which removes the drift between regenerated and committed bytes.

## Before you upgrade

- No data-directory, configuration, or database migration steps: startup and the control SQLite schema are identical to 0.1.8, which already carries the Refinery migration lineage. Replacing the binary is optional for operators who do not use the SDK.
- No new platform migration is published between 0.1.8 and 0.1.9; an 0.1.8 database opens unchanged.
- Snapshot restore still requires matching release and schema identity; take a new snapshot after upgrading.

## Install or upgrade

An existing receipt-managed installation can upgrade directly:

```console
ocd upgrade 0.1.9
```

For a new system-wide installation, download and review the installer before elevating it:

```console
curl -fsSL -o install.sh https://raw.githubusercontent.com/elliothux/open-compute/v0.1.9/scripts/install.sh
less install.sh
sudo env OPEN_COMPUTE_RELEASE_TAG=v0.1.9 sh install.sh
sudo /usr/local/bin/ocd setup --yes --system
```

For the default user-owned installation, run the reviewed installer without `sudo`, then run `ocd setup --yes`. Verify with `ocd --version`, `ocd config check`, `ocd doctor`, and `ocd capabilities --json`.

## Security

There are no published security advisories specific to 0.1.9. Management-plane credentials keep their boundaries: deployer and admin tokens never enter tenant isolates, internal listeners stay loopback-only and capability-scoped, and per-generation internal tokens never appear in argv, environment, logs, status, metrics, errors, or tenant-visible responses. The mandatory-`baseURL` design keeps the SDK from defaulting any request to `api.cloudflare.com`.

## Known limitations

- Pre-1.0: an official compatibility claim exists only for an `ocd` and `@open-compute/sdk` of the same `X.Y.Z`.
- Selected routes the pinned official SDK does not implement are intentionally absent from the SDK surface even though `ocd` supports them (`PUT …/workers/scripts/{script_name}/usage-model` and `PUT …/r2/buckets/{bucket_name}`); the exclusion is recorded in the selection manifest and the SDK never hand-forges an official method.
- The first npm publish is bootstrapped with an explicitly authorized, short-lived `NPM_ACCESS_TOKEN`; npm provenance via trusted publishing is deferred and tracked as follow-up work.
- Current upstream drift stays `blocked` per the refresh contract and does not move pins: schema HEAD adds optional AI Search `use_ocr`/`custom_metadata` fields and a Queue create `jurisdiction` field that `cloudflare@7.1.0` does not yet express, and Wrangler 4.131.2 awaits its own coordinated evidence review against the pinned 4.127.1.
